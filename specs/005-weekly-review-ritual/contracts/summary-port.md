# Contract: The summary port

**Feature**: 005-weekly-review-ritual

A named interface with exactly one call site, supplied by injection, following the shape `TranscriptionPort`
already established: core owns the interface and the call site, a client supplies the engine. **No provider
ships in this feature.**

```ts
/**
 * Drafts a summary of a finished week from the review's own record.
 *
 * Optional in every sense: none ships, none is required, and the review completes
 * normally with none supplied. A draft is a proposal — nothing it returns is
 * recorded unless the user hands it back through `complete()`.
 */
export interface SummaryProvider {
  /** Attribution, recorded beside the text. Shown to the user before it runs. */
  readonly name: string;
  draft(record: ReviewRecord): Promise<string>;
}
```

---

## Why it is a port and not an extension API

Principle V defers loaders, discovery, and public extension surfaces; Principle III requires everything to
work offline. A port satisfies both: the interface is internal, injected at one construction site in
`main.ts`, with no registry, no lookup, and nothing exported for a third party to register against. It is
exactly what `TranscriptionPort` is — and whisper is proof the shape works for an expensive, optional,
failure-prone engine.

**Why build it now rather than in Feature 8**: the call site is inside review completion, and the record's
shape is decided here. Retrofitting attribution into a log format after users have months of weekly files on
disk would mean changing what a completed review means retroactively. Deciding now what a generated summary
looks like in the file — attributed, separate, accepted — is what keeps the later addition additive.

---

## Absent means absent

`ReviewServiceDeps.summary` is optional, and **absent means no summary** — the opposite of
`ReviewServiceDeps.policy`, where absent means the default rules.

The asymmetry is the point, and it needs saying out loud because the two look alike:

- A **rule** that could be dropped by forgetting an argument is a bypass, so policy must default to
  enforcing (Principle V).
- A **summary** that appeared because an argument was forgotten would be generated text nobody asked for, so
  summaries must default to nothing (FR-076).

With none supplied, `draftSummary()` returns `{ available: false }`. That is the shipped configuration and
is not an error: a client renders no summary affordance at all, rather than a disabled or broken one
(FR-103).

---

## Acceptance is structural

```ts
draftSummary(): Promise<
  | { available: false; failure?: string }
  | { available: true; text: string; provider: string }
>;

complete(input: {
  note?: string | null;
  summary?: { text: string; provider: string };
}): Promise<ReviewResult>;
```

Core records only what the caller passes back in `complete()`. There is no path — no flag, no option, no
default — by which a draft core produced is written to the log without being handed back (FR-105). Declining
is therefore the default and costs nothing: the log is byte-for-byte what it would have been.

An accepted summary is written to its own `## Summary (generated by <provider>)` section, separate from
`## Note`, attributed, and never merged into or written over the user's own words (FR-106, FR-107). A reader
opening the file in a year can always tell whose sentences are whose.

---

## The payload boundary

`draft()` takes a `ReviewRecord` — the parsed review for that week, and nothing else. It does **not** take a
`VaultStore`, a path, or a callback that could fetch one.

```ts
/** Exactly what a provider sees. Derived from log/YYYY-Www.md, nothing more. */
export interface ReviewRecord {
  week: WeekId;
  started: string;
  inbox: InboxStepRecord | null;
  projects: ProjectReviewRecord[];
  waiting: WaitingReviewRecord[];
  topThree: TopThreeStepRecord | null;
  note: string | null;
}
```

Project files, `inbox.md`, `identity.md`, `policy.md`, `waiting.md`, and `top-three.md` are never passed
(FR-108). The boundary is a **type**, not a rule someone has to remember: a provider that wanted more would
have to change core to get it, which is a visible change rather than a quiet one.

**Inspectable before it is sent** (FR-109): the client can render the exact record — it is plain data it
already has — and the review view shows it before invoking a provider.

**Nothing leaves the machine by default** (FR-110). Sending anything anywhere requires the user to supply and
configure a provider deliberately. Guarded by a test: a stub provider records what it was handed, and the
fixture puts distinctive marker strings in a project file, `inbox.md`, and `identity.md` that must not appear
in the payload (SC-015c).

---

## Failure is never blocking

A provider that throws, hangs, times out, is unreachable, or is misconfigured yields
`{ available: false, failure }` — never a rejected promise out of `draftSummary()`, and never a path that
prevents `complete()` (FR-111). The failure is surfaced plainly and the review completes with the user's note
alone.

A provider returning empty or whitespace-only text is treated as no draft. Nothing is recorded, and an empty
`## Summary` section is never written.

---

## What is deliberately absent

- **A loader, registry, or discovery mechanism.** One injection site in `main.ts`.
- **Any exported registration API.** `SummaryProvider` is exported as a *type* so the project can use the
  seam deliberately, not so a third party can plug into it. Publishing an extension API is a promise that is
  expensive to take back.
- **A shipped provider, stub or otherwise.** Feature 8 brings one, as a client of this port.
- **A timeout policy.** Whether to give up, and after how long, is the supplied provider's business; core's
  contract is only that a failure of any kind cannot block completion.
- **Any use of the port outside review completion.** One call site. A second one would make this an
  extension surface by accretion.
