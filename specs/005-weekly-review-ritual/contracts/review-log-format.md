# Contract: `log/YYYY-Www.md`

**Feature**: 005-weekly-review-ritual

One file per ISO week, holding the review of that week — **while it is in progress and after it is
finished**. There is no separate state file (research R2).

The filename uses the identifier Feature 4 defines, `YYYY-Www`, computed by `isoWeek()`. This settles the
reconciliation Feature 4 handed forward: the ROADMAP sketched `log/YYYY-WW.md`, and the identifier wins, so
a log filename and a `top-three.md` section heading for the same week read identically and sort
chronologically as plain text.

---

## In progress

```markdown
# Weekly review 2026-W33

status: in progress
started: 2026-08-14
step: projects

## Inbox

- 2026-08-14 11 items, warned, proceeded

## Projects

- 2026-08-14 migration-cutover status active → parked
- 2026-08-14 hiring-loop milestone done Panel trained on the new rubric
- 2026-08-14 vendor-review no change

## Waiting for

## Top three

## Note
```

Every section exists from the moment the file is created, so a reader always sees the shape of the ritual and
an empty section means "nothing recorded here yet" rather than "this file is malformed". `status: in
progress` is the first line of the preamble because it is the thing a person opening the file needs to know
first (FR-057).

Completion changes exactly three things: `status`, a new `completed:` line, and the content appended to
`## Top three`, `## Note`, and — only if a draft was accepted — a `## Summary` section. Nothing already
written is rewritten (FR-091's habit, applied to the log).

## Grammar

```text
preamble    := "status: " ("in progress" | "complete")
               "started: " date
               ["completed: " date]
               "step: " ("inbox" | "projects" | "waiting" | "top-three")

inbox-line  := "- " date " " count " items, " verdict ", proceeded"
             | "- " date " inbox clear"

project-line := "- " date " " slug " " action-detail
action-detail := "no change"
              | "status " from " → " to
              | "milestone done " text
              | "next action " ("set" | "cleared" | "changed")
              | "outcome set" | "dri set" | "milestones set"

waiting-line := "- " date " @" owner " " days "d " action " — " text
              | "- " date " project " slug " " days "d " action

top-three-line := "- finished: " text
                | "- slipped: " text
                | "- committed " week-id ": " text
```

| Field | Rule |
|---|---|
| `date` | Local calendar date, `YYYY-MM-DD`. The same local-date habit `waiting.md` and milestones use. |
| `verdict` | `warned` only. A blocked step is not passed, so `blocked` never appears. |
| `days` | Whole days untouched at the moment the subject was surfaced. |
| `action` (waiting) | `followed up`, `received`, or `left`. |
| `slug` | The project's filename stem — its identity everywhere else, so the log joins to it. |

Lines are appended in the order decided. Order within a section is chronological by construction and is
never re-sorted.

---

## Parsing rules

The same two rules that govern every other document in this vault:

1. **Parsing never fails.** An unknown section, prose the user typed under a heading, a hand-written line
   that matches no grammar above — all are carried through untouched and ignored by the reader. A file the
   app refuses to open is a file the app has taken hostage.
2. **Writing is surgical.** Only the lines being appended are added; every other byte is reproduced exactly.
   The vault is git-tracked, and a read that reformats turns every app open into a diff.

A hand-edited log is shown as it reads and is never repaired, reordered, or regenerated (FR-072). A completed
review is read-only in the application (FR-011); the file stays editable by hand, which is the deliberate
escape hatch for correcting history.

---

## What the reader derives

- **Which projects have been walked** — those with at least one line in `## Projects`. This is the resume
  position; no cursor is stored (research R3).
- **Whether a step was passed** — from `step:`, not from section contents, because a step may pass with
  nothing to record (an empty waiting-for list).
- **Nothing else.** The log does not carry a copy of any project's fields, any milestone's state, or any
  waiting-for item's status. Those live in their own files, and a second copy would drift.

---

## Retention

Never pruned, rotated, compacted, or summarised away (FR-069). One file per week is roughly 52 short files a
year. `log/` is created when the first review starts and not before — no file is created speculatively
(Principle IV's habit, matching `policy.md` and `identity.md`).
